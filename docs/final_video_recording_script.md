# SchedX-Agent 最终展示视频录制台本

建议视频时长：6～8 分钟。  
录屏工具：FinalShell 录屏、OBS 或其他桌面录制工具。  
演示环境：openEuler 24.03 LTS SP4，`/root/SchedX-Agent`。

## 录制前准备

1. 将终端字体调到 18～20，窗口最大化，分辨率建议 1920×1080。
2. 不要展示 `/etc/schedx/llm.env`、API Key、SSH 私钥和密码。
3. 在开始录屏前执行：

```bash
cd /root/SchedX-Agent
source .venv/bin/activate
git pull --ff-only gitlink master
bash scripts/demo_cleanup.sh
clear
```

4. 开始录屏后执行：

```bash
cd /root/SchedX-Agent
source .venv/bin/activate
bash scripts/demo_recording_story.sh
```

脚本会在每一幕结束后等待按 Enter。讲解完当前画面，再按 Enter 继续。

## 第 1 幕：项目定位、内核适配与真实环境（约 60 秒）

画面会展示 openEuler、当前内核、资源控制功能、自定义调度功能和大模型状态。

旁白：

> 本项目名为 SchedX-Agent，主要解决在线服务受到后台任务干扰的问题。当前演示运行在比赛要求的 openEuler 24.03 LTS SP4 上。
>
> 这里还需要说明一个实际的内核适配问题：SP4 安装介质自带的内核没有开启可扩展调度功能，无法直接加载自定义调度器。为完成真实调度验证，我们在 SP4 内核基础上启用了这项能力，当前内核版本末尾带有 schedx1 标识，系统检测结果也显示可扩展调度功能已经可用。这不是模拟输出，后续会真实加载调度策略并检查运行状态。
>
> 同时，Agent 保留了兼容方案：如果目标机器不支持自定义调度，它会自动退回资源控制模式，而不是直接停止工作。当前环境既可以加载自定义调度器，也可以通过资源控制组限制后台任务，并由 DeepSeek 大模型协助选择优化方案。下面看到的识别、调整、效果检查和自动恢复，都在这台真实虚拟机中执行。

画面出现环境信息时，依次指出：

- 操作系统是 openEuler 24.03 LTS SP4
- 内核版本末尾包含 `schedx1`
- “可扩展调度功能”显示可用
- Agent 运行模式为真实自定义调度模式，而不是模拟模式

看到 `READY` 后按 Enter。

## 第 2 幕：识别在线服务与后台干扰（约 50 秒）

脚本会启动 nginx 与 stress-ng 混合负载，并输出分类结果。

旁白：

> 现在 Agent 开始观察系统中正在运行的任务。它识别出五个 nginx 进程属于需要快速响应的在线服务，同时发现 stress-ng 正在持续占用处理器，因此把当前环境判断为混合负载场景。
>
> 这一步不是只按处理器占用率粗略判断。Agent 会结合进程名称、启动命令、资源使用情况和父子关系进行识别，并通过安全名单排除自身程序、远程登录和系统管理进程，避免把关键控制进程错误地放入低优先级资源组。

[指向“混合负载”“nginx x5”和“stress-ng”三行，停留两秒，然后按 Enter。]

## 第 3 幕：大模型提出方案，安全规则负责把关（约 60 秒）

脚本会调用 `llm-plan`，显示策略来源、模式、目标、置信度和结构化参数。

旁白：

> 根据刚才识别到的混合负载，DeepSeek 提出了优先保护 nginx 响应速度的方案。屏幕同时给出了本次方案的可信度，以及在线服务和后台任务的优先级。在线服务的优先级明显更高，用于优先保障用户请求；后台任务仍保留运行机会。具体数值以本次屏幕输出为准。
>
> 需要强调的是，大模型只有建议权，没有直接操作系统的权限。它输出的是固定格式的参数，随后还要经过目标白名单、参数范围和风险规则检查。只有检查通过后，执行模块才会进行真实调整；如果大模型不可用，Agent 也能自动使用本地规则继续工作。

[指向“方案来源”“保护对象”“可信度”和两行优先级，然后按 Enter。]

## 第 4 幕：自动执行并检查效果（约 2～3 分钟）

脚本调用当前主程序：

```bash
python3 scripts/run_competition_demo.py \
  --output results/video-recording \
  --report reports/video-recording.md \
  --llm-policy \
  --compact \
  --duration 3 \
  --repeats 1 \
  --connections 8 \
  --threads 2 \
  --batch-threads 2 \
  --stress-cpu 2
```

等待期间旁白：

> Agent 现在开始完整执行。第一步对比默认调度、只限制后台资源、只使用自定义调度，以及 Agent 联合优化四种方案。第二步换成批处理计算任务，检查系统是否只对 nginx 场景有效。第三步真实应用 DeepSeek 给出的方案并进行小范围试运行。第四步使用更严格的安全门槛，验证不合格方案能否自动恢复。
>
> 每个候选方案都不是模拟计算。系统会先真正调整资源控制参数并加载调度策略，再测量每秒请求数、最慢百分之一请求的延迟和后台任务进度。测量完成后，Agent 才决定保留还是恢复。因此，画面中出现“已自动恢复”并不代表方案没有执行，而是表示方案已经执行和验证，但没有同时满足安全要求。

> 本次录制使用短时参数验证流程完整性，正式性能结论来自多轮重复实验，短时结果不用于宣称稳定性能提升。

脚本完成后按 Enter。

## 第 5 幕：实验结果与自动恢复（约 90 秒）

画面会显示四种方案对比、第二类批处理任务，以及小范围试运行的接受和恢复结果。

旁白：

> 现在看第一组在线服务实验。默认方案下，每秒处理约六万一千三百个请求，最慢百分之一请求的延迟是二点九三毫秒。只限制后台资源时，前台吞吐虽然提高到约八万次，但后台任务进度只剩百分之二十八点三六，说明这种方法是用明显压制后台任务换取前台性能，不适合作为长期的均衡方案。
>
> 只使用自定义调度时，后台任务仍保持百分之九十八的进度，最慢百分之一请求延迟降低到零点三七六毫秒。Agent 联合优化后，每秒请求数相对默认方案下降百分之零点九九，属于很小的吞吐代价；最慢百分之一请求延迟下降百分之八十二点零一，同时后台任务仍保持百分之九十八的进度。这说明本轮联合方案的主要收益不是增加吞吐，而是在基本不影响处理能力和后台任务的情况下，显著改善最慢请求的响应时间。
>
> 第二组换成批处理计算任务，用来证明 Agent 不只针对 nginx 有效。加入后台干扰后，处理能力从每秒约一万六千四百次下降到约八千九百次，较慢请求延迟从零点三六毫秒增加到二点九四毫秒，说明干扰确实生效。
>
> Agent 优化后，处理能力恢复到每秒约一万四千三百次，相比干扰场景提升百分之六十点九；较慢请求延迟从二点九四毫秒降低到零点三六毫秒，下降百分之八十七点七六。后台任务仍保留百分之三十点零五的进度，高于预设的百分之二十五公平性底线，因此系统将这组结果标记为可信。
>
> 接下来是 DeepSeek 方案的小范围试运行。最慢百分之一请求延迟下降百分之八十四点四一，每秒请求数只下降百分之零点零二，后台任务仍保持百分之九十点三七。三个指标都在安全范围内，因此 Agent 判定这个候选方案可以接受。这说明大模型提出的建议只有通过真实测量后，才会成为可用策略；演示结束时，系统仍会统一恢复默认状态。
>
> 最后一项使用了更严格的安全门槛，专门验证自动恢复能力。这个候选方案虽然让最慢百分之一请求延迟下降百分之八十四点五三，但没有达到人为设置的更高门槛，因此系统不保留它，并自动恢复十九项设置，删除九个临时资源组和八个调度策略。
>
> 这两次小范围试运行共同展示了完整决策逻辑：满足响应速度、处理能力和后台任务进度要求的方案会被接受；没有满足全部安全条件的方案，即使部分指标变好，也会自动恢复。Agent 的作用不是盲目执行大模型建议，而是用真实数据决定方案应该保留还是撤销。

[依次指向“Agent 综合效果”“第二类任务”“常规小范围试运行”和“严格安全检查”。讲完后按 Enter。]

以上数字对应本次真实运行结果。如果重新录制后数字发生变化，应按照屏幕上的实际数据朗读，不要沿用本次数字；结论也必须与屏幕上的“改善、回退、已接受或已自动恢复”保持一致。

## 第 6 幕：清理与总结（约 45 秒）

画面应显示：

```text
后台干扰仍在运行 : 否
资源控制仍有残留 : 否
自定义调度状态   : 已关闭
CLEAN: 演示环境已恢复
```

旁白：

> 最后一幕显示环境已经恢复。这里的“恢复设置数量为零、删除资源组数量为零”，不是恢复功能没有执行，而是上一幕在方案被拒绝时已经完成了十九项设置恢复和临时资源清理，所以最终检查时已经没有新的内容需要处理。
>
> 现在后台干扰已经停止，临时资源组没有残留，自定义调度也已关闭。整个过程形成了“发现问题、选择方案、执行优化、检查效果、接受或恢复、生成报告”的完整闭环。SchedX-Agent 的价值不只是调整一次参数，而是让大模型提出建议，再用真实数据和安全规则决定方案能否留在系统中。

> 此外，项目同时兼顾内核能力差异：支持可扩展调度的环境执行真实自定义调度，不支持的环境自动使用资源控制方案，因此既能体现内核调度创新，也具备在不同 Linux 环境中落地运行的能力。

## 常见术语的中文讲法

录制时优先说右侧中文，不需要反复念英文缩写：

| 技术名词 | 演讲时的中文说法 |
|---|---|
| procfs | 进程信息 |
| PSI | 系统压力 |

| workload | 工作负载或运行任务 |

## 录制结束后的检查

停止录屏前再展示一次版本：

```bash
git rev-parse --short HEAD
python3 -m schedx status
```

最终提交版本应与 GitLink `master` 一致。

录制完成后，将视频命名为：

```text
项目展示.mp4
```

替换仓库根目录和 `初赛作品提交材料/` 中的旧视频，再提交：

```bash
git add 项目展示.mp4 初赛作品提交材料/项目展示.mp4
git commit -m "Update final demonstration video"
git push origin master
```

视频不得超过 100 MB。
