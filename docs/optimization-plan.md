## 目标与实施原则

优先让执行结果可信、失败能够恢复、混合负载持续获得运行机会，再优化自适应策略和性能。每个阶段交付可独立验证的改动，沿用现有 Agent、Skill 和 Controller 结构。

本计划中的性能门槛为拟定验收标准，需要在固定的虚拟机配置上建立基线；现有审查已确认本地和 openEuler 的 167 项测试通过，但尚未验证修复后的真实内核行为。

## 阶段 1：修复失败处理和回滚可靠性

**涉及模块**

`schedx/agent/executor.py`、`schedx/agent/loop.py`、`schedx/controllers/cgroup_controller.py`、`schedx/skills/act_skill.py`、`schedx/skills/scx_skill.py`、`schedx/skills/rollback_skill.py`、`schedx/main.py`。

**工作内容**

1. 定义一致的执行结果：成功、无动作、显式降级、失败、已回滚和回滚失败。JSON、Skill 返回值和 CLI 退出码使用同一判断依据。指标不足另标记为 `inconclusive`，不能记录为性能优化成功。
2. 检查外部命令退出码，修正 `chrt` 参数和不存在的 nice 接口；保存修改前的 nice、调度策略和 CPU affinity，使这些操作也能恢复。
3. 区分“调度器正在运行”和“本次策略成功写入”。部分写入失败时恢复已经修改的条目；允许的 cgroup-only 降级必须显式记录，并验证剩余控制是否生效。
4. 回滚成功后再移除对应记录。恢复失败的记录采用原子替换保存，支持同进程重试和进程重启后重试；汇总 cgroup、scx、eBPF 三种后端的结果。
5. 统一使用 context 的状态目录。先为现有日志增加锁和原子更新，并兼容已有记录格式，后续再按会话划分。
6. 每轮建立独立的候选动作状态。规划失败立即终止本轮，不能使用上轮残留动作；在资源修改后发生异常或候选验证失败时进入恢复流程。
7. 回滚未完成时停止新的资源修改，保留恢复证据。恢复已有 scx 策略时还原修改前的值，不能仅删除当前 map 条目。

**必须覆盖的测试**

- 外部命令非零退出、命令不可用、BPF map 全部/部分写入失败。
- 规划失败后 scx/act 不执行；动作异常触发恢复；回滚失败不会报告“已回滚”。
- 恢复写入第一次失败、第二次成功；重启进程后仍能读取并恢复失败条目。
- 明确区分目标已退出与恢复失败；重复回滚保持幂等。
- JSON 最终状态与 CLI 退出码一致；原有可用策略不被其他操作的回滚删除。

**完成条件**

审查中的失败误报和回滚记录丢失均有回归测试，且全部通过；虚拟机完成一次故障注入及恢复，不留下未解释的资源设置或策略。

## 阶段 2：补足跨队列公平性

**涉及模块**

`scx/scx_agent.bpf.c`、`scx/scx_agent_user.c`、`schedx/controllers/scx_controller.py`、`schedx/scx_daemon.py`。

**工作内容**

- 为普通队列设置非零服务保障，先保留现有加权虚拟时间方案；比较若干服务间隔，依据实测决定默认值。
- 普通/批处理保障和后台保障同时生效；daemon 的自适应调整不能重新将普通队列保障关闭。
- 收集每类任务的实际运行时间和等待时间，区分 enqueue 次数、dispatch 次数和 CPU 时间，避免以队列次数推断资源份额。
- 明确最低进度和最长等待时间指标，将普通任务、编译任务及控制进程纳入 canary 检查。
- 在当前 openEuler 回移内核上验证 cpu.weight、cpu.max 与自定义 sched_ext 的实际关系，记录支持范围和降级行为。

**验收场景**

- 低延迟队列持续非空，同时运行普通计算、后台干扰和控制命令。
- 单核竞争、多核竞争、CPU affinity 受限、某个队列为空及突发负载切换。
- 至少 10 分钟连续压力运行，记录调度器状态变化和任务最长等待时间。

**完成条件**

- 分支模型中的普通队列零服务问题消失，并有真实内核运行证据。
- 活跃任务在连续采样窗口内保持进度；没有任务停滞导致的非预期调度器退出。
- 沿用当前已配置场景的 25% 后台进度保留门槛；普通任务等待预算作为独立门槛，经基线测量后确定并写入配置。
- 与修复前可复现配置比较 RPS、P99 和各类任务进度，给出公平性与服务性能的取舍。

## 阶段 3：让持续运行和收敛判断符合实际指标

**涉及模块**

`schedx/agent/decision.py`、`schedx/agent/loop.py`、`schedx/skills/canary_skill.py`、`schedx/skills/verify_skill.py`、`schedx/policies/router.py`。

**工作内容**

- 移除“三轮即收敛”的条件，将最大轮次、连续故障、性能稳定和用户停止分别处理。
- `max_rounds=0` 保持长期监控；收敛后减少不必要的策略修改，继续观测负载变化。
- 将 canary 的吞吐、尾延迟和进度指标接入轮次历史。指标缺失、无动作或执行失败不能证明性能收敛。
- 收敛依据可配置的有效样本数和稳定窗口，避免单次短样本或瞬时波动决定停止。
- 保留路由冷却和连续观察机制；负载类型变化后重新评估，避免重复写入相同策略。
- 对失败恢复使用有上限的退避；输出准确退出原因和恢复状态。

**完成条件**

- 三轮均失败时不会提示收敛；无限监控模式能运行超过三轮。
- “稳定负载 → 新增干扰 → 干扰消失”的实验中，Agent 能观察变化、调整并稳定下来。
- 相同策略重复评估不会增加无意义动作或无限增长回滚日志。
- 报告中的收敛判断能追溯到有效指标和完整执行结果。

## 阶段 4：修复动态网络策略更新

**涉及模块**

`ebpf/net_policy.bpf.c`、`schedx/controllers/ebpf_controller.py`、`schedx/skills/ebpf_skill.py`。

**工作内容**

- 在令牌桶锁内检测策略参数变化，同步速率和 burst，并约束剩余 tokens；评估需要时增加策略版本字段。
- 明确速率单位，统一用户态参数、BPF 计算和报告中的 bit/s 或 byte/s 表达。
- 验证速率上调、下调及 burst 缩小，处理频繁更新和并发发包。
- 将实际丢包和“超限但仍放行”的统计分开，保证低延迟类放行计数准确。
- 验证 map 容量、策略删除、cgroup 退出后的桶及统计清理。

**完成条件**

- 同一个 cgroup 不重建、BPF 程序不重载即可切换速率；在约定的观察窗口内达到新限速。
- 重复切换策略无旧参数残留；低延迟放行不会被报告为实际丢包。
- 有真实发包测试与原始吞吐、丢包和 map 状态记录。

## 阶段 5：增强并发与工具执行可靠性

**涉及模块**

`schedx/agent/context.py`、`schedx/controllers/cgroup_controller.py`、`schedx/skills/scx_skill.py`、`schedx/scx_daemon.py`、`schedx/controllers/scx_controller.py`、`schedx/tool_runner.py`。

**工作内容**

- 按操作/会话记录资源所有者及原始状态；同一资源的修改需要协调，回滚只能恢复本操作拥有的修改。
- 验证 PID 对应的进程身份，降低进程退出及 PID 复用后作用于其他任务的风险。
- 给调度器命令读取设置截止时间，持续消费 stderr，记录 daemon 中断和实际降级原因。
- 给工具执行增加可配置超时；输出流式保存并限制内存占用。
- 为短工具增加启动握手，在策略注册完成后开始实际工作，准确报告策略是否成功应用。
- 超时、中断和异常时清理整个工具进程树、对应策略及空 cgroup；明确处理预期长期运行的子进程。
- 检查孤儿策略和统计条目，确保恢复/清理可以重复执行。

**完成条件**

- 至少四个并发工具操作不会丢失恢复记录或删除其他操作的策略。
- 一个操作失败或回滚，不影响其他操作的正常设置。
- 超时和中断后，无残留工具进程、专属策略或非预期 cgroup；控制调用在规定时间内返回。
- 短工具和大量输出工具均有覆盖测试；正常路径与失败路径均记录实际后端和清理结果。

## 阶段 6：综合验收和性能回归

**自动检查**

- 保持现有测试通过，加入阶段 1–5 的必要回归测试。
- 建立 Linux 单元测试 CI；真实 sched_ext/eBPF 验证使用具备对应内核能力的独立环境，明确标识未运行或跳过的场景。
- 检查相似实现的调用方，将兼容入口改为转发，保留单一实现；统一代码换行，减少无内容变化的差异。

**实机实验**

- 默认调度、cgroup-only、native sched_ext 和组合 Agent 使用相同负载配置比较。
- nginx/Redis 加 CPU 干扰、批处理吞吐和工具执行实验，各至少重复五次，轮换实验顺序。
- 输出 RPS/QPS、P99、批处理进度、后台进度、普通任务等待时间、控制开销、错误率及置信区间。
- 先完成 30 分钟混合负载稳定性测试，再完成至少两小时的并发、负载变化和恢复实验。
- 每组实验记录提交、内核、参数、实际策略写入成功数、后端状态、原始输出及最终清理状态。

**拟定发布门槛**

- 所有正确性和恢复测试通过，没有未恢复状态或未解释的资源残留。
- 调度公平性达到阶段 2 确定的门槛，没有非预期调度器退出。
- 主要吞吐或尾延迟相对固定基线出现超过 5% 且重复实验显示稳定的退化时，阻止发布并分析原因；公平性调整造成的取舍需要单独报告和明确决策。
- 没有有效指标或置信区间时，结论标记为证据不足，不直接宣称性能提升。

## 交付与推进方式

按阶段提交小范围变更，每个变更包含问题、修复、必要测试和实机证据。阶段 1 完成后再进行涉及真实调度策略的验证；一个阶段验收失败时先解决对应问题，再进入依赖它的阶段。

首个实施包聚焦阶段 1：保留失败的回滚记录、统一失败传播、阻断无效动作。它完成后，后续公平性和性能实验才能得到可信结果。

## 第二轮：持续监测与证据质量 — 2026-10-04

在已验收的 `e75ef3a` 上继续细化阶段 3 和阶段 5。复现发现：三轮各自收益变化均小于 1% 时，即使候选实际 P99 为 10、50、2 毫秒，旧判断仍报告稳定；阶段日志也没有长期容量限制，停止原因和稳定依据未完整保存到会话文件。

本轮完成以下改进：

- 稳定判断要求模式、目标、专家和策略参数一致，并同时检查实际目标值的波动及每轮变化。缺失、无效或非有限指标不能建立稳定状态。
- 开放 `--stable-window`（2–128 轮，默认 3）和 `--stable-tolerance`（百分比，默认 1）；均衡模式缺少吞吐时可依据真实延迟指标。
- 会话记录保存最近 128 轮、最多 1000 条阶段日志、稳定判断理由、目标值及退出原因。失败、恢复未完成和中断也保留最终记录。
- 已符合目标的 nice、调度策略和等价 CPU-affinity 设置跳过重复修改及恢复日志写入。

本地与虚拟机 241 项测试通过。针对性实机验证包含私有进程上的 30 次重复属性设置和完整恢复，以及真实环回 HTTP 采样驱动的六轮监测状态变化。稳定标记能在延迟从约 102 毫秒升到 402 毫秒后撤销，再在后续稳定样本中重新建立。此实验使用采样适配器验证监测状态机，不是新性能收益声明；本轮未改动原生 BPF 调度器，上一轮五次性能及两小时内核记录继续作为其版本证据。详见 [第二轮报告](../reports/optimization-continuous-20261004/report.md)。不重建定时任务，机器继续保持运行。
