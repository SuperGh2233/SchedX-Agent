## 已完成的实质改进

下表“此前”仅指已核对的优化基线 `58903fe`；初赛 SHA 确认后需重新核对正式初赛对照列。

| 方向 | 此前的问题或限制 | 本轮实际改进 | 实现及验证入口 |
| --- | --- | --- | --- |
| 调度公平性 | 普通和批处理共享队列，普通服务保障为零；混合负载可能停滞 | 四类独立队列、普通和批处理服务机会、交互与普通轮转、按运行时间反馈调节后台服务 | `scx/scx_agent.bpf.c`；首轮性能及长期报告 |
| 故障恢复 | 回滚失败可能删除记录；部分失败仍报告成功 | 原子恢复日志、失败保留与重试、准确退出码、跨候选恢复既有设置 | `schedx/state.py`、`controllers/process_state.py`、恢复回归测试 |
| 多任务可靠性 | 共享状态竞争、PID 复用和策略互相清理风险 | 会话/事务所有权、进程身份检查、状态目录隔离、四个并发工具验证 | `controllers/cgroup_controller.py`、`skills/scx_skill.py`、`tests/test_recovery.py` |
| 持续监测 | 三轮即停止；小收益变化可能掩盖剧烈实际指标变化 | 依据真实目标值和同一策略判断稳定，窗口/容差可配置，稳定后继续观测 | `agent/decision.py`、`agent/loop.py`、第二轮报告 |
| 动态网络策略 | 已存在令牌桶可能继续使用旧速率；放行和丢包统计混淆 | 同一 cgroup 动态同步速率和 burst，区分真实丢包与超限放行 | `ebpf/net_policy.bpf.c`、真实发包记录 |
| 工具执行 | 短工具可能先执行后注册；超时和输出没有有效边界 | 启动握手、超时、输出上限、进程树清理和策略回收 | `schedx/tool_child.py`、`schedx/tool_runner.py`、生命周期验证 |
| 可追溯与工程质量 | 持续运行记录不足，重复设置不断追加恢复条目 | 保存有限轮次与阶段记录、明确停止原因、进程设置去重；测试从 167 增至 241 | 会话 `metrics.continuous`、Linux 回归测试和 CI 配置 |

这些改动涉及操作系统调度、策略执行、恢复机制和连续监测的真实行为，属于实质性实现变化。代码行数、换行调整、报告体积和历史数据归档不作为实质提升的论据。

## 当前可使用的实测证据

- 在四 vCPU openEuler SP4 虚拟机上，`59c1ca4` 与 `58903fe` 做五次成对性能对比：nginx/Redis P99 分别下降 49.48% 和 30.67%；批处理吞吐下降 2.26%，该取舍需同时披露。
- 每对旧版/新版实验均达到至少 25% 后台进度保留门槛。指标有 95% 置信区间和原始数据，不能改写为通用 Linux 性能结论。
- 原生调度版本通过 30 分钟和两小时实验；两小时有 1428 个样本和 59 次成功的超时恢复，交互类最长排队等待约 76 毫秒。
- 当前实现版本在本地及虚拟机通过 241 项测试；第二轮真实 HTTP 采样验证稳定状态随指标变化撤销与重建，私有进程 30 次属性设置去重及完整恢复通过。
- 第二轮 HTTP 实验使用采样适配器验证监测状态机，不能作为完整自主策略链或新增性能收益的证据。

性能对比对象是优化基线，不是已确认的官方初赛提交。正式材料只有在初赛 SHA 和对应实验确认后，才能使用“相较初赛提升 X%”的表述。

## 提交前的必要补齐

1. 根据初赛已提交记录确认准确 SHA/标签；保存可恢复的版本与提交信息，避免凭日期或 README 推测基线。
2. 核对该提交是决赛分支的祖先，生成忽略换行噪声的语义差异和关键功能对照。
3. 对官方初赛版本与最终决赛候选使用同一环境和负载进行成对实验。此前数据可作历史证据，但不同基线和不同软件版本的结果不能合并。
4. 将说明书、PPT、证据矩阵和演示脚本同步到决赛候选；固定候选提交或标签，使源码、运行程序和引用数据对应。
5. 在演示环境核对启动路径与程序版本。目前优化代码保存在本地分支和虚拟机隔离目录，原运行目录仍保留，不能默认现场正在运行优化版。

## 需要披露的边界

- 当前 SP4 native 调度器不执行硬 CPU 配额；需要硬配额时采用默认调度器下的 cgroup-only 模式。
- 任务等待预算是实测验收阈值，不是硬实时保证。
- GitHub CI 配置已完成，但尚未推送运行。
