## 1. 让验收门禁覆盖失败请求与无效配置

**已确认的问题。** `schedx/benchmark/wrk_parser.py` 没有解析 socket 错误和非成功响应；`schedx/policies/verifier.py` 只据延迟、吞吐及调度/后台指标判断候选。向解析器提供 P99 为 9 毫秒、RPS 为 1000、100 次超时和 20 次非成功响应的输出，仍只得到延迟与吞吐字段；相对 P99 为 10 毫秒、相同 RPS 的基线，门禁返回 `accepted`。直接在候选字典中提供 `socket_errors` 也未参与判断。

直接调用 `CanaryVerifier(max_regression_percent=float("nan"))` 时，P99 从 10 毫秒退化到 100 毫秒仍返回 `accepted`。构造器的负数检查无法拒绝非有限阈值。CLI 的非负数值解析已拒绝非有限值，因此此复现针对程序化配置接口；默认 5% 阈值不受这一配置问题影响。

**建议改动。**

- 在各入口统一验证阈值的类型、有限性与范围；拒绝 NaN、无穷值和不应作为阈值的布尔值。
- 保留 wrk 完成请求数、测量时长、四类 socket 错误及非成功响应计数；确认 Redis 等工具也有明确的失败指标。
- 单独检查失败/超时与有效吞吐。socket 事件计数不一定等于失败请求数，不能将其与响应错误简单相加后除以完成请求数。成功响应比例和 socket 事件采用各自明确的口径。
- 门槛同时考虑绝对错误和相对基线变化；允许预期错误的场景需显式配置。要求错误指标的场景缺少该指标时标记为证据不足。

**验收。** 错误输出的解析、正常无错误输出、缺失字段、无效计数、非有限配置，以及“延迟改善但错误增加”的拒绝路径都有针对性测试。保存原始输出和门禁理由；不能单凭外部工具退出码判定请求成功。wrk 的官方实现会打印错误统计，正常汇总路径随后返回 0，见 [wrk 源码](https://raw.githubusercontent.com/wg/wrk/master/src/wrk.c)。

已检查此前归档中全部 40 份原始 wrk 输出，未发现非零 socket 错误或非成功响应。这是输出计数核查，不证明所有错误来源均已覆盖，也不推翻原有性能结果。复现输入、门禁结果、归档指纹和逐文件检查结果见 [探索证据](../reports/optimization-route-exploration-20261005/findings.json)。

## 2. 建立真正对应初赛版本的性能对照

**已确认的缺口。** 当前 `scripts/run_optimization_benchmarks.py` 的报告基线硬编码为 `58903fe`，实验名包含 `redis`，调用参数包含 `--redis-port`。初赛 `b0591a1` 的 benchmark 接口包含 `redis-latency`，没有当前结构化 `redis` 场景，参数与结果格式也有差别。仅替换基线目录不能保证对测有效。

**建议改动。**

- 从实际 Git 对象或显式版本清单生成基线和候选身份，记录完整 SHA、源码与二进制指纹及构建环境，移除硬编码版本说明。
- 用共同的外部测量工具驱动相同服务、请求、干扰和采样窗口；版本适配只处理启动和结果格式，保留初赛算法行为。
- 先选双方确实支持的共同场景。初赛缺少的功能单列为功能新增，不能将“未支持”当作零性能再计算增益。
- 固定环境、CPU 绑定和预热，交替旧新版顺序，保留至少五个有效成对样本；同时保存失败指标、后台进度、等待时间和置信区间。
- 区分原生调度算法收益、资源组合策略收益和完整自主 Agent 收益，避免把不同运行路径的结果合并。

**验收。** 报告能从每行数据追溯到实际版本与运行方式；无效或未支持场景不计入样本。主要指标出现置信区间显示稳定超过 5% 的退化时分析并阻断该性能主张；各版本均需达到约定的后台进度门槛。

现有 nginx/Redis P99 下降 49.48%/30.67%、批处理吞吐下降 2.26% 对应 `59c1ca4` 对 `58903fe`，不是正式初赛对比。`069276c` 的 241 项测试与持续监测实验属于另一组版本证据。详见 [决赛改进对照](final-round-improvements.md) 和 [版本清单](../reports/final-round-comparison-20261004/baseline.json)。

## 3. 验证完整自主优化链在负载变化时的行为

**当前边界。** `scripts/verify_continuous_monitor.py` 用真实 HTTP 测量适配器替换 `_run_one_round`。它验证了监测稳定标记随延迟变化撤销与重建，以及任务属性去重/恢复；没有对完整 Probe → Analyze → 路由 → 策略 → Act → Canary → Verify/回滚链进行此次变负载验收。

**建议实验。**

1. 创建可销毁的私有服务和计算干扰，记录初始调度状态。依次运行稳定、增加干扰、移除干扰三个阶段。
2. 让真实 Agent 各阶段入口执行，记录分类、专家、参数、动作、实际写入结果、候选指标、门禁和恢复。失败恢复未完成时禁止新动作。
3. 对照相同负载下的固定策略、规则选择和完整 Agent。若增加 LLM 对照，独立标记模型、提示和调用成本，避免将模型参与等同于性能收益。
4. 注入一个可控候选失败，观察拒绝及恢复；先用短实验确认流程，再运行长期实验。所有修改只作用于本实验拥有的资源。

**验收。** 负载变化能触发有依据的重新评估；同策略稳定时不持续重复写入；候选拒绝后的状态可验证恢复。结合 P99、成功吞吐、后台进度、最长等待、决策耗时、策略切换数与清理结果评价。未测到收益时报告功能正确与性能证据不足，不能强行宣布更优。

**比赛价值。** 可展示系统根据变化执行和撤销资源策略，并把每个决策与实际效果对应起来，比单独展示稳定标记更能体现 Agent 的完整能力。

## 4. 让硬限制和软优先级匹配后端能力

**已验证限制。** `cpu_control_support()` 对当前 SP4 native 报告 `cpu_max=not_enforced`；`ToolRunner` 在执行结束后追加相关警告。前期实测已确认写入 `cpu.max` 不等于该原生调度器执行配额。

**建议分两步。**

- 先增加启动前的能力判断：明确请求是硬 CPU 上限还是软优先级；无法满足硬限制时拒绝启动或显式选择已验证支持的配置。状态报告区分配置值、支持状态和实测结果。
- 再评估原生硬配额：核对当前回移内核的接口，研究组预算或可用带宽回调；这是内核实验方向，需要独立压力和恢复验证。

默认调度器下的 cgroup-only 路径适用于已验证支持的硬配额场景。若全局调度器由其他操作拥有，不能为了本工具降级而停止它；`--no-scx` 跳过本工具策略注册也不保证全局原生调度器已停止。

Linux 文档说明 sched_ext 的 cgroup 控制效果由 BPF 调度器实现决定，接口也没有跨内核稳定性保证；当前上游文档不能证明 SP4 回移内核具有相同能力。参考 [sched_ext 文档](https://docs.kernel.org/scheduler/sched-ext.html) 和 [cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)。

**验收。** 请求不支持的硬限制在工具启动前得到明确结果；支持路径通过真实 CPU 时间测量核对；后端退出和失败后能恢复原有状态。原生实现需额外验证不同线程数、突发和竞争场景下的配额与公平性。

## 5. 从类别公平性扩展到 Agent 之间的公平性

**待验证假设。** 当前按类别设置 DSQ，交互/普通采用轮转及有上限的权重时间片，批处理/后台采用任务级虚拟时间。它保障不同类别获得运行机会，但尚不能从这些机制直接推出同类 Agent 的总资源份额公平。线程更多的 Agent 是否占据额外份额，需要实测。

**先测再改。** 在同类、同配置下比较两个 Agent 的线程比例 1:1、1:16 和 4:4；固定总负载，记录每个 Agent 的有效进度和最长等待。若出现与目标不符的组间份额差异，再研究按 Agent/cgroup 累计运行时间的组虚拟时间或两层调度。

另一个实验目标是减轻目前约 2.26% 的批处理吞吐取舍。可以逐项比较服务间隔、时间片、运行时间反馈和共享 DSQ 开销；多核局部队列也可作为后续方向。每次只改变一项，保留等待和后台进度门禁，不能通过取消保障换取表面吞吐。

**验收。** 先定义目标是每任务公平还是每 Agent 公平；再比较组份额、有效吞吐、P99、最长等待及控制成本。当前只有四 vCPU 虚拟机证据，NUMA、大规模多核和局部队列收益需要其他环境验证。

## 6. 用真实策略结果改进下一次选择

**代码观察。** `PolicyRepository` 保存接受、拒绝、证据不足次数与最后指标；`ExpertRouter` 的评分来自分类和建议模式及其衰减历史，未将这些策略结果用于评分。已有结果记录不等于已有基于收益的学习策略。

**建议路线。** 先按负载上下文保存有效收益、错误、恢复代价和样本可信度，避免将不同场景混合。给专家选择加入受限的历史反馈，仍保留冷却、连续观察和可执行参数白名单。参数搜索或上下文 bandit 放在这一基础完成之后，小范围试探并通过 Canary 门禁。

**验收。** 与静态规则和固定最佳策略分别对照，统计有效收益、拒绝次数、切换次数、试探成本及恢复。证据不足不计为正收益；重复选择坏策略应有可解释原因或抑制机制。跨负载留出验证，避免仅适合单个演示场景。
