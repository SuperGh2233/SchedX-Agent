# 第三轮实机验收与继续优化

本轮连接恢复后，在四 vCPU openEuler SP4 虚拟机上验证了本地实现，并修复实测暴露的进程范围、恢复和重复试探问题。当前实现为 `47440e27bd5af2fa3c6672a951615dbfea7ee0e2`，生产源码 SHA-256 为 `ae15710fcf2a22ed96bd4a635d36602b7a57e0b1fbf5b6a88d0529e828197638`。本地与 Linux 均通过 **412 项测试**；最新完整场景仍在执行，整体验收不标记完成。

## 已完成的代码改进

| 实测问题 | 修复后的行为 | 实现节点 |
| --- | --- | --- |
| 没有后台进程时，零后台占比被误判为饥饿 | 明确区分不存在后台负载与后台存在但没有进度；保留原始零值，验收元数据使用“不适用” | `6272221` |
| 采样限定 PID 后，按进程名执行的动作仍匹配整机 | 执行器再次过滤声明范围，显式 PID 和直接迁移也受同一范围约束 | `aa7e45c` |
| 负载移除后，恢复此前策略尝试写入已经退出的进程 | 按 PID 与启动时间识别存活进程；移除过期 cgroup 策略，只恢复仍存在的任务 | `6c4ce12` |
| 候选策略被安全拒绝后，连续三次拒绝使监测退出 | 成功恢复的有效候选拒绝继续观察；执行错误、无效指标与恢复失败仍计入故障预算或停止 | `7bbb1db`、`4c712c4` |
| 同一负载上下文反复试探已经被拒绝的策略 | 恢复后初次观察三轮，同上下文再次拒绝逐步延长至 6、12、24 轮，持续测量健康；进程身份、压力档位、参数或测量要求变化即重新试探 | `4e95368`、`34b7758` |
| 硬 CPU 上限正常限流后，反馈建议 `cpu:high`，会取消上限 | 保留用户的硬上限，成功的正常限流不建议无效重试；内存压力等反馈仍可返回 | `4e95368` |

观察轮记录为 `observed_healthy`，候选接受记录为 `accepted`。观察轮不写入控制，不累计候选成功，也不计算优化收益；请求错误、缺失指标与后台无进度仍不能通过。稳定判断继续检查真实目标值波动和策略身份，并加入负载上下文，不能把不同进程/负载的样本拼成稳定窗口。

这些变化补强了可靠执行和依据真实结果控制试探的能力；它们不等同于新增了基于收益训练的专家路由或原生组调度算法。

## CPU 控制合同

`79905fb` 的真实内核短测已经通过：10% 硬配额的两秒忙循环实际消耗约 **0.205 秒 CPU**；硬配额工具执行期间，项目内 native 启动在挂接前被阻止；native 已启用时硬配额请求在工具执行前被拒绝；明确选择软优先级时能够运行，但报告 `cpu.max=not_enforced`。清理完成后 native 状态为 disabled。

配额反馈修正已在 `7162f92` 复验：两秒忙循环消耗 0.20443 秒 CPU，正常限流没有建议重试或取消上限，其余合同及清理检查通过。当前工具执行代码与该复验版本一致。证据见 `remote-checkpoint/evidence/cpu-contract-7162f92/summary.json`，旧短测资料也保留。

## 环境、原始资料与边界

根分区已满，新源码、构建产物与原始证据全部放在 `/tmp/schedx-acceptance-20261005-79905fb`；没有删除用户文件或覆盖原工作目录。初次构建因系统 bpftool 与所需 struct_ops 骨架不兼容失败，保留输出后使用已有匹配构建工具完成构建。后续 Python 修正复用原生程序和 eBPF 对象，并核对对应 C/头文件逐字节一致；源码版本与复用构建的来源分别写入清单。

虚拟机挂起后墙上时间约落后客户端 12 小时。保留双方时间，时长、CPU 进度使用单调时间/CPU 累计值，没有修改机器时间设置。

当前 SP4 native 仍不执行硬 `cpu.max`。此次改进提供前置能力检查、执行路径选择和准确反馈，没有实现原生内核配额。正式初赛全项目收益、固定策略与自主 Agent 的成对比较、不同线程数 Agent 的组间公平性及最新 Python 路径长期验收仍没有完整通过证据。

自动跟进任务保持删除状态。结束后关机是用户重新授权的独立步骤，须等所有必要验收完成且证据保存到本地；当前不执行关机。

## 静态参数诊断与当前复验

共同吞吐权重下，固定服务间隔 40 的后台进度保留约 16%–18%；固定间隔 20 的五轮补充实验也未达到 25%。两组各保留全部 45 次测量，综合均为 `not_accepted`，后续阶段未启动。另一个单轮诊断测量 64、40、20、5、1 五个间隔，并读取实际内核配置和策略 map：写入正确，但只有间隔 1 的该轮达到约 45% 保留。这是机制诊断，不是正式性能增益证据。

试验性固定参数修改已撤回，吞吐启动间隔保持 40。完整 Agent 会依据运行时间反馈调节间隔，固定值不能代表其实际行为。新增 `shared-adaptive` 对测仅在批处理场景为双方应用同一现有反馈规则、15%–25% 运行时间目标和吞吐权重；初赛缺少新的 class-metrics 命令，共同适配器使用双方已有的 cgroup runtime 数据。调整和确认均独立记录，不能将它称为未经适配的初赛完整系统。

独立控制器还修复了零进度边界：有后台任务排队但 CPU 时间为零时也会启动反馈，不存在后台工作时不会凭空调节。该边界已通过针对性回归测试。

候选 `47440e2` 独立验收流水线 PID 为 52340，状态位于虚拟机 `evidence/final-validation-47440e2/pipeline.json`。它依次运行五轮共享反馈对测、46 轮完整自主流程、30 分钟综合及两小时变负载/周期超时恢复。当前正在第一阶段；阶段不通过就停止后续实验。实验稳定容差仍为 10%、生产默认 1%，候选退化和后台进度门槛没有放松。

此前完整证据已保存到本地，压缩包 SHA-256 为 `eaf6bdedfd82935b990c7b6603b00f7f9fced0881d1fab21dda96aa21d84677d`，解压后有 888 个普通文件。当前复验启动前，原工作目录与备份的 2393 个普通文件全部内容一致；原安装程序保持初始 SHA，原 nginx 五个进程均回到原服务 cgroup。运行中的新数据仍需在终态后追加归档，当前检查点不能代表当前流水线已完成。
