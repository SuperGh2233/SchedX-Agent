# SchedX-Agent 代码审查 — 2026-10-03

审查基线：GitHub `main`，提交 `58903fe`。刷新远程引用后确认本地与 `origin/main` 一致。

虚拟机 `/root/SchedX-Agent` 为 `master`，提交 `63f76e0`，有大量未提交内容。比较并归一化换行后，Agent 循环、cgroup 控制器、动作执行器、调度守护进程、BPF 调度器、工具执行器这六个关键文件与本地内容一致。本报告主要以 GitHub 版本定位问题，并对虚拟机做只读环境检查及现有测试验证。

## 结论和验证范围

现有结构已经包含规则/LLM 提案、策略路由、cgroup/sched_ext 控制、canary 验证和回滚。最需要改进的是失败处理、回滚可靠性，以及长时间混合负载下的公平性。

- 本地现有测试：167 项通过。首次有 3 项因 macOS 临时目录过长而无法绑定 Unix socket；使用短临时目录后全部通过。
- openEuler 虚拟机现有测试：167 项通过。
- 额外故障模拟确认了回滚记录丢失、失败被报为成功、连续循环失败处理和错误的收敛判断。这些模拟没有修改真实调度策略或系统 cgroup。
- 调度饥饿结论来自代码分支和简化模型；网络策略更新问题来自静态检查。两者尚未通过真实内核压力实验验证。
- 检查时虚拟机的 sched_ext 状态为 `disabled`，因此测试通过不能证明当前真实 BPF 调度器的公平性、动态限速或性能提升。
- 本次未修改业务代码、未提交或推送。

## 需要优先修复的问题

### 1. [P1] 回滚失败后仍删除恢复记录

位置：`schedx/controllers/cgroup_controller.py:149–162`；`schedx/skills/rollback_skill.py:41–46`。

`rollback()` 遇到写入失败时记录 `restore_failed`，随后无条件删除 `rollback.json`。`RollbackSkill` 的成功标志只取决于 eBPF 清理结果，没有把 cgroup 或 scx 恢复失败计入最终结果。

故障模拟结果：CPU 权重仍为 `50`，恢复到 `100` 的写入失败，记录文件却已不存在。再次执行回滚无法从记录中重试该恢复。

建议：仅移除成功恢复或已确认无须恢复的条目；原子保存剩余失败条目；明确区分“目标已退出”和“恢复失败”；汇总三类后端的恢复结果，失败时返回可重试状态。

### 2. [P1] 普通/批处理队列可能被持续的低延迟任务饿死

位置：`schedx/controllers/scx_controller.py:41`；`scx/scx_agent.bpf.c:221–233`。

`SCX_FAIRNESS_DEFAULT_CLASS_INTERVAL = 0` 禁用了普通队列的服务保障。dispatch 在低延迟队列有任务时总是优先取它，只周期性保障后台队列。批处理和未分类任务共用普通队列；调整同一队列内的权重无法解决跨队列饥饿。

按当前分支模拟三个队列始终非空的 10,000 次 dispatch：低延迟 9,847 次、后台 153 次、普通队列 0 次。这是分支模型结果，不是真实 CPU 时间比例。未分类的控制进程也没有因此获得跨队列保障。

建议：为普通队列设置非零服务上限，或依据等待时间/实际运行时间做跨类分配；测试持续低延迟负载下编译任务和控制进程的最长等待时间。Linux 的 sched_ext 会在可运行任务停滞时退出 BPF 调度器并恢复默认调度，因此这一问题还可能破坏调度器持续运行。参见 [Linux sched_ext 文档](https://docs.kernel.org/scheduler/sched-ext.html)。

### 3. [P1/P2] 执行结果没有准确传播失败

位置：`schedx/skills/scx_skill.py:84–98`；`schedx/agent/executor.py:146–155、171–176、191–196`；`schedx/skills/act_skill.py:28`；`schedx/main.py:200–201`。

- **P1，调度策略写入：** 模拟 daemon 可用、所有写入返回 False 后，`ScxSkill` 仍返回 `ok=True`、`scx_status=active`。独立调度路径也没有按失败数决定成功标志。应区分调度器运行、策略全部应用、部分应用和降级，并恢复部分写入。
- **P2，外部命令：** `chrt`、`taskset` 等使用 `check=False`，却未检查退出码便报告 `ok`。`chrt --pid batch <pid>` 的参数本身也不正确；在虚拟机验证得到 `invalid priority argument: 'batch'`。应使用正确选项，并检查退出码和错误输出。
- **P2，异常汇总：** 动作返回 `status=failed` 时，`ActSkill` 的失败列表没有覆盖它。模拟 taskset 不可用后，执行结果含失败，但 skill 仍返回成功。
- **P2，nice：** `os.sched_set_priority` 不存在，在虚拟机也已确认。这一路径实际会触发 AttributeError，进入外层回滚。应改用 Python 支持的优先级接口，并保存对应的原始设置。
- **P2，CLI：** `cmd_optimize` 不论最终报告成功、失败还是回滚，都返回退出码 0。自动化实验无法仅凭退出码判定优化是否完成。

建议建立统一的执行结果和错误传播规则，并加入上述故障回归测试。让 JSON 状态、skill 成功标志、回滚触发条件和 CLI 退出码一致。

### 4. [P1] 连续循环在策略失败后继续执行，并误报回滚完成

位置：`schedx/agent/loop.py:195–234`。

`_run_one_round()` 在 `policy_result.ok=False` 后仍继续运行 scx、act 等修改阶段。上下文在轮次间复用，如果失败的策略阶段未更新动作，后续可能继续使用上一轮动作。返回状态又统一写成 `failed_rolled_back`，没有依据 `rollback_result.ok` 区分恢复失败。

故障模拟确认：策略阶段失败，act 仍被调用；回滚阶段也失败，报告仍为 `failed_rolled_back`。

建议：每轮建立独立的候选动作状态；规划失败时立即结束本轮；仅执行已通过验证的候选；分别报告应用失败、成功回滚和回滚失败，并在恢复未完成时暂停新的资源修改。

### 5. [P2] “持续运行”三轮后无条件退出，并宣称收敛

位置：`schedx/agent/decision.py:99–109`；`schedx/agent/loop.py:151–153`。

`should_stop()` 只要历史长度达到 3 就返回 True。`max_rounds=0` 也因此无法持续监控；三轮均为 probe_failed 的模拟仍输出 `optimization converged`。轮次结果没有提供该判断读取的 `improvement`，当前停止条件不能证明性能收敛。

建议：把最大轮次、故障熔断和性能收敛设为独立条件及退出原因；收敛依据有效 canary 指标、足够样本和连续稳定观测；长期监控模式在负载变化后继续评估。

### 6. [P2] 动态网络限速更新没有同步已有令牌桶

位置：`ebpf/net_policy.bpf.c:113–139`；`schedx/controllers/ebpf_controller.py:293–308`。

令牌桶只在首次创建时复制策略的 rate 和 burst，后续 refill 使用桶内缓存。用户态更新只写 `net_policy_map`，不会更新或失效已有桶。因此同一个 cgroup 的速率从旧值切到新值后，已有桶仍按旧速率补充令牌。

建议：引入策略版本，或在桶锁内检测并同步 rate/burst，调整剩余 tokens。用同一 cgroup 连续切换不同速率的真实发包测试验证更新立即生效。

## 后续改进方向

1. **补足故障和长期运行测试。** 优先覆盖恢复失败重试、BPF map 写入失败、daemon 中断、策略阶段失败、连续负载变化及普通队列最长等待时间。167 项现有测试已通过，但没有覆盖本次复现的关键错误。
2. **提高多 Agent 状态可靠性。** cgroup 回滚记录目前采用共享文件的读—改—写，缺少文件锁和原子替换；不同执行可能丢失记录或回滚彼此的修改。建议按会话/操作划分日志、标记资源所有者，并验证进程身份以降低 PID 复用影响。此项为设计审查，未做并发实机复现。
3. **限制阻塞和资源残留。** 调度控制器等待提示符没有截止时间；工具执行的 communicate 没有超时，并将全部输出保存在内存。建议加入请求/工具超时、持续消费错误输出、输出上限或流式落盘，以及对子进程树和剩余 cgroup 的清理。对“短工具在策略注册前已经结束”的竞态，可用启动握手验证并修复。
4. **让性能证据对应实际启用的后端。** 每次实验记录提交、内核、sched_ext 状态、实际应用成功数、配置和机器资源；继续使用轮换/配对实验与置信区间，同时报告普通队列、批处理和后台任务的进度。针对当前 openEuler 回移内核，核对自定义 sched_ext 实际实现的 cpu.weight/cpu.max 语义，不能仅依据文件写入成功推断调度约束生效；上游文档说明这些控制的支持取决于 BPF 调度器，具体内核行为仍需验证。参见 [Linux sched_ext 文档](https://docs.kernel.org/scheduler/sched-ext.html)。
5. **减少维护漂移。** 审核 `schedx/loop.py` 与 `schedx/agent/loop.py` 等相似模块的外部调用，把兼容入口改为转发，保留单一实现；统一换行；增加 Linux 单元测试 CI 和单独的真实内核验证流程。

推荐修复顺序：保留失败的回滚记录 → 准确传播执行失败并停止无效动作 → 普通队列服务保障 → 真实收敛判定 → 网络策略动态更新 → 多 Agent 和长期运行验证。
