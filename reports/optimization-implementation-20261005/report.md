## 已实现

### 请求质量门禁

- 所有 Canary 阈值拒绝非有限值、负数、不合适的类型和越界比例；程序化配置不能再用 NaN 绕过退化门槛。wrk 配置要求正整数时长、连接数和线程数。
- 保存完成请求数、测量时长、四类 socket 事件和非成功响应。异常错误行不会被当作零错误。
- 响应错误比例与 socket 事件/秒采用不同分母，分别检查绝对门槛和相对基线变化；默认容许错误为零，可明确设置允许值。
- 有完整请求计数时按成功响应吞吐判定，并让持续监测使用同一有效吞吐。缺少必要请求质量数据返回证据不足，实际 Canary 会要求恢复；无穷的派生增益不会进入报告。

入口：`CanaryVerifier`、wrk 解析器、`VerifySkill` 和 `--canary-max-*` 参数。首次复现证据保留在 [探索记录](../optimization-route-exploration-20261005/findings.json)，不覆盖失败历史。

### CPU 控制与并发协调

- `tool-run` 的有限 `cpu.max` 默认要求硬配额，使用已经建立配额文件的默认调度路径；不会为这类工具启动 native 调度器。
- 全局 native 已启用或启动前无法建立配额时，实际工具命令不执行，返回明确原因。`--cpu-limit-mode soft` 显式选择软优先级，状态记录实际后端支持。
- 硬配额工具持有共享后端锁，原生调度器持有独占锁；锁描述符随子进程执行保留。项目内的调度器启动不能与活跃的硬配额工具竞争。
- 对不遵守此协调锁的外部调度器变更，硬配额工具在运行中轮询检测，停止进程树并返回失败。该检测有采样间隔，不构成针对外部管理员修改的硬实时保证。
- 原有原生公平性验证明确使用 `soft`，避免把其 CPU 配额配置误写成已执行的硬上限。

这些检查没有实现 SP4 native 的内核配额功能。该平台已验证的 `cpu.max` 限制仍成立；新能力是执行路径选择和准确失败处理。

### 私有实验与版本核验

- `--scope-pid` 和程序化 `scope_pids` 限定真实 procfs 采样。空列表不会退回整机范围，非法范围在规划前失败；需要显式列出希望纳入的进程。
- 源码逐文件与指定 Git 对象核对，报告实际完整提交、源码及程序指纹；构建清单必须与这些值匹配。清单匹配是完整构建证据的一部分，还需保存真实构建命令与输出。
- 旧版对测脚本移除 `58903fe` 硬编码；在资源修改前拒绝不兼容的初赛 benchmark 接口。
- 私有 nginx、Redis、干扰和批处理负载使用独立端口、进程组及 cgroup；清理仅针对这些资源。HTTP 503 注入只作用于私有服务。
